## Rules that apply to every step

1. **No live write without the owner's approval** (R35b). Read-only queries (P1-P6) are not writes.
2. **Full backup immediately before the first live write**, which is Migration 01 (R48, D11), and tell
   the owner where it is stored *before* running 01. Recommended (owner decision): take a fresh backup
   before the first write of each later stage as well, and always before `02.down` (it deletes data).
3. **Run the whole file at once** in the SQL Editor (role `postgres`). Each file is one transaction
   (`BEGIN ... COMMIT`): if any statement fails, nothing is applied. Do **not** use `supabase db push`:
   `supabase_migrations.schema_migrations` is empty on the live project (snapshot
   `db/applied_migrations.json`) and two repo files share version `202610050001`, so every file would be
   treated as pending.
4. **Built-in guards** stop a file before it changes anything. The error tells you which guard fired:

   | Error starts with | Meaning | What to do |
   |---|---|---|
   | `ORDER:` | A prerequisite migration is missing or a later one is still applied | Run the named file first |
   | `DRIFT:` | A live function body differs from the 2026-10-18 snapshot this file was built from | Do not force it. Re-base the file on `pg_get_functiondef(...)` and rebuild |
   | `PRECONDITION:` | Missing object, or the role does not bypass RLS | Run as `postgres` in the SQL Editor; check P4 |
   | `ABORT:` | `backtest_trades` has rows | Export them first (owner decision) |
   | `ALREADY SUPERSEDED:` | 01 re-run after 02 | Nothing to do; 01 is in effect |
   | `DATA LOSS:` | `02.down` would delete backtest accounts/trades | Back them up, then confirm (see the 02 rollback) |
   | `IN USE:` | Something still calls a function that 06 drops | Do not run 06; patch instead |
   | `canceling statement due to lock timeout` | `lock_timeout = 10s` hit | Retry at a quieter moment |

5. **Rollbacks run only in reverse order** (06, 05, 04, [03], 02, 01). The guards enforce
   04 before 02 and 02 before 01.
6. **Function bodies come from the LIVE snapshot** (`scratchpad/db/fn_*.sql`, 2026-10-18), never from
   older repo files (repo/live drift is documented in the findings). CRLF bodies are normalised to LF;
   the drift guards compare bodies with all spaces, tabs, CR and LF removed:
   `md5(translate(prosrc, E' \t\r\n', ''))`.

## Step P: pre-flight (read-only), right before the backup

Run in the SQL Editor and save the full output next to the backup (`preflight.txt`).
- **P1** prints, per function, the GRANT lines that restore today's EXECUTE privileges. 06's
  rollback needs them for an exact restore; the `[EXACT-ACL]` lines of 02.down / 05.down refer to them.
- **P2** captures `backtest_trades` exactly. 01's rollback recreates it; if a column shows a typmod
  (e.g. `numeric(18,8)`), adjust the rollback before ever using it.

## Step B: full backup (R48 / D11), immediately before Migration 01

Tooling and location per D11 (owner decision): portable PostgreSQL 17 client binaries (no Docker,
nothing installed into the repo), a folder outside the repository and outside OneDrive, e.g.
`C:\Users\kadir\WaweJournal-Backups\<UTC timestamp>\`. The folder holds personal data: keep it private.
Template (PowerShell; exact `pg_dump` flags to be confirmed with `supabase db dump --dry-run` as D11
says, because a few Supabase-internal objects may need exclusions):

```powershell
$ts  = (Get-Date).ToUniversalTime().ToString('yyyyMMddTHHmmssZ')
$dir = "C:\Users\kadir\WaweJournal-Backups\$ts"
New-Item -ItemType Directory -Force $dir | Out-Null
# Connection string: Supabase Dashboard -> Connect -> Session pooler (port 5432).

$conn = 'host=aws-0-<region>.pooler.supabase.com port=5432 dbname=postgres user=postgres.<project-ref> sslmode=require'
& "<pg17>\bin\pg_dump.exe" --dbname="$conn" --format=custom --file="$dir\full.dump"
& "<pg17>\bin\pg_dump.exe" --dbname="$conn" --schema-only --file="$dir\schema.sql"
Remove-Item Env:PGPASSWORD
& "<pg17>\bin\pg_restore.exe" --list "$dir\full.dump" | Out-File -Encoding utf8 "$dir\full.dump.toc.txt"
Get-FileHash "$dir\*" -Algorithm SHA256 | Format-Table -AutoSize | Out-File -Encoding utf8 "$dir\SHA256SUMS.txt"
```

output is saved as `preflight.txt` in the same folder, and **the folder path has been reported to the
owner**. Storage objects are not part of a database dump (no candle files exist before Stage 3B).

## Rolling back

Reverse order only: **07 -> 06 -> 05 -> 04 -> 03 -> 02 -> 01 -> 00** (00 last, and only for a verified regression: it re-opens the IDOR). Roll back the client of a stage before its
database step when the client depends on it (Stage 4 page before 02.down, Stage 5+6 client before
04.down/05.down). Each rollback is idempotent and refuses to run out of order. `touch_updated_at()` is
never dropped (it pre-exists live and `trg_journals_updated_at` uses it).

ACL note: 02 revokes the (unused) `anon`/`PUBLIC` EXECUTE on `delete_journal(uuid)` and 05 does the same
for `list_journals()`. Both functions reject callers without `auth.uid()` anyway. The rollbacks keep
that hardening; each has a commented `[EXACT-ACL]` line to restore the pre-migration ACL exactly.

## Additions beyond the decision record (please review)

All are in the files and covered by the local tests; each can be removed without touching the rest.
1. `BACKTEST_NOT_OWNER` guard at the top of both trigger functions: BEFORE ROW triggers run before the
   RLS `WITH CHECK`, so without it any API caller (even `anon`, whose `auth.uid()` is NULL) could send a
   row with another user's `user_id` and read that user's plan/account count
   (`BACKTEST_LIMIT_EXCEEDED:10`) or journal ownership (`INVALID_JOURNAL`) from the SECURITY DEFINER
   code. It applies to JWT roles `anon`/`authenticated`; admins are exempt (they can read every row
   anyway, and an admin deleting a user's journal must not fail in the `ON DELETE SET NULL` cascade);
   `postgres`, `service_role` and auth cascades are not affected.
2. `backtest_accounts.id` and `.symbol` immutable (D3 lists `user_id` only): mirrors are keyed
   `backtest:<account id>:` and every trade must carry the account symbol.
3. A journal link must point to an **active** own journal on INSERT and on relink
   (`check_prop_account_limit` checks `is_active` on INSERT only).
4. The quota check takes a per-user `pg_advisory_xact_lock`, so two parallel creates cannot both pass
   (the prop template has that race).
5. `backtest_account_trades`: identity/entry columns immutable (id, user_id, account, symbol, direction,
   lot, entry_price, entry_time, created_at) and a closed trade is final; SL/TP stay editable while open.
6. Extra value guards: prices `> 0` and finite (unconstrained `numeric` accepts `NaN` and `±Infinity`),
   `isfinite()` on the timestamps, `rr_ratio >= 0`, NaN guards on every numeric.
7. Drift guards, run-order guards, an RLS-bypass precondition, and the data-loss confirmation in 02.down.
8. The OPTIONAL columns are a separate `ALTER TABLE ... ADD COLUMN` block (easy to delete), with a
   one-line DECLINE switch after it.

## Open points for the lead (the decisions are implemented as written)

1. **Name length (R10/D3).** `CHECK (char_length(btrim(name)) BETWEEN 1 AND 60)` accepts a name padded
   with spaces to any length. One-line fix: add `AND char_length(name) <= 60` (or require
   `name = btrim(name)`).
2. **Initial vs. current SL/TP (D4/D5).** Open positions must keep SL/TP editable (the reload resumes
   them), so `stop_loss`/`take_profit` hold the *current* levels. D5 mirrors the *initial* levels and
   `rr_ratio` is defined on them. After an edit the initial levels are gone, and `trg_calc_pnl`
   recomputes `trades.rr_ratio` from whatever SL/TP the mirror sends. Options: add
   `initial_stop_loss` / `initial_take_profit` (set at open, immutable), or mirror the final levels and
   accept a final-level R:R.
3. **Cleanup scope on account delete (D5).** The DELETE trigger only removes mirrors in
   `OLD.journal_id` (plus NULL-journal rows). If a client sync upsert is in flight while the account is
   relinked, mirrors can land in the old journal after its cleanup and would survive a later account
   delete. Options: drop the journal predicate in the DELETE case (the account is gone, so all its
   mirrors of that user can go), and/or the optional trades guard trigger (reject a mirror whose
   `journal_id` is not the account's current journal).
4. **Numeric ranges (D3).** `rr_ratio numeric(10,2)` overflows above 99,999,999.99 (TP far away with a
   1-point SL) and `pnl numeric(14,2)` with absurd lot sizes: the insert fails with SQLSTATE 22003. The
   engine should send NULL/clamp R:R and cap lot sizes, or the DB adds an upper bound on `lot`.
5. **Admin rights (D3).** Admins can read and delete other users' backtest rows but cannot modify them
   (`WITH CHECK user_id = auth.uid()`), unlike `prop_accounts` where admins can update. Confirm.
6. **R48 frequency.** D0 reads R48 as one backup before Migration 01. Recommended: also before the first
   write of every later stage and before any data-losing rollback.
7. **Baseline re-run hazard.** `supabase/migrations/202608190001_security_baseline.sql:142-151` creates
   policies on `backtest_trades` without a `to_regclass` guard, so re-running that historic file after 01
   fails with 42P01. Nobody should re-run it; optionally add a guard there.
8. **Version check.** Local tests ran on {{PG_VERSION}}; live is 17.6. Everything used exists in 17
   (`hashtextextended`, `isfinite`, `to_regprocedure(text)`, row `IS DISTINCT FROM`). A dry run on a
   PostgreSQL 17 restore of the schema-only dump (D0) would remove the residual risk.
